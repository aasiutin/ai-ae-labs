## Захист від витоку ключів

`.gitignore` у корені репозиторію не пускає в git файли з ключами:

```gitignore
apps/.env
.env
.env.*
!.env.example
```

Pre-commit хук [`.githooks/pre-commit`](../../../.githooks/pre-commit) запускає
gitleaks на staged-змінах і блокує коміт, якщо знайде секрет:

```sh
#!/bin/sh
gitleaks git --staged --redact --verbose || {
  echo "❌ Коміт заблоковано: у staged-змінах знайдено секрет."
  exit 1
}
```

Хук увімкнено через `git config core.hooksPath .githooks`. Це налаштування
лежить у `.git/config` і не переїжджає з клоном, тому в кожному новому клоні
його треба виконати знову.

## Context-stress сценарій

Станом на 01.10.2026. Модель — `gpt-5.6-luna` (провайдер `openai`), інструкція
агента та сама, що й у діалогах вище.

### Чому в цьому прогоні немає пошуку

- `geminitool.GoogleSearch{}` — вбудований інструмент Gemini. Адаптер OpenAI
  у pi-go передає моделі лише function-інструменти, а цей мовчки відкидає
  (`pi-go/internal/provider/openai_responses.go`, `oaiGenaiToolsToResponses`).
- Власний `web_search` OpenAI pi-go вмикає лише явно, через змінну
  `PI_OPENAI_WEB_SEARCH`. У цьому прогоні вона не задана.

Отже, модель отримала інструкцію «перед рекомендацією обов'язково використай
пошук», але не отримала жодного інструмента.

### Висновок

Агент знає лише те, що лежить у контексті. Решту він має або отримати (пошук, RAG чи інструмент, залежно від того, де дані), або чесно визнати, що не знає. У критерії головне — «замість вигадки», і цей тест агент пройшов на всіх трьох питаннях. Ваша думка «RAG не обов'язковий, бо залежить від обсягу і джерела даних» якраз показує ментору, що ви розумієте різницю, а не повторюєте шаблон.

### Як вимірювалось

- **Латентність** — один виклик моделі, від запиту до останньої відповіді,
  з логу `[llm call]` обгортки `timedLLM`. Console викликає модель без
  стрімінгу, тому `ttfb` = `total`. Час компіляції `go run` сюди не входить.
- **Токени й пошук** — з того самого рядка логу: `UsageMetadata` і
  `GroundingMetadata.WebSearchQueries`, які повертає провайдер. Перед
  бенчмарком `timedLLM` доповнено цими полями
  ([`main.go`](main.go), тест — [`timed_test.go`](timed_test.go)); код
  однаковий для обох моделей.
- **Пошук.** У кожної моделі свій вбудований пошук: Gemini — Grounding with
  Google Search (`geminitool.GoogleSearch{}`), luna — OpenAI `web_search`,
  який pi-go вмикає змінною `PI_OPENAI_WEB_SEARCH=1`. Змінна задана для обох
  прогонів; на Gemini вона не впливає. Тобто порівнюється «модель + її
  власний пошук», а не модель окремо.
- **Вартість** = (in − cached) × input + cached × cached_input +
  (out + thoughts) × output + searches × ціна пошуку. Кількість пошукових
  запитів із логу прирівняно до кількості оплачуваних запитів (Gemini) і
  викликів (OpenAI), тому вартість пошуку приблизна.

## Карта термінів

Ці визначення описують поняття в контексті цієї лабораторної, а не лише їхнє
загальне значення.

| Термін | Де саме в цій лабі | Що це означає для вас |
|---|---|---|
| **LLM** | `createModel` у `provider.go` | Мовна модель, яка генерує план вихідних. Змінна `MODEL` дає змогу замінити модель без зміни коду агента. |
| **Provider / routing** | `providerDefaults` + `chooseModel` у `provider.go` | Не термін зі словника лекції, але шоста вісь рішення тут стає кодом: те саме ім'я моделі напряму й через шлюз — різні ціна, латентність і спостережуваність. |
| **Prompt / Instruction** | поле `Instruction` у `llmagent.Config` і запит користувача | Інструкція задає роль, формат і обмеження агента. Запит користувача визначає конкретне завдання. Разом вони формують prompt для моделі. |
| **Context window** | інструкція, запит, історія діалогу та результати пошуку в одному виклику | Обмежений обсяг інформації, який модель може використати для поточної відповіді. |
| **Tool** | `geminitool.GoogleSearch{}` у полі `Tools` | Зовнішня дія, яку агент може викликати для отримання актуальних подій, погоди, цін та адрес. |
| **Agent** | `llmagent.New(...)` разом із `launcher` | LLM, інструкція, інструменти та код, який керує їхньою взаємодією. |
| **RAG** | окремого RAG-конвеєра в цій лабі немає | Підхід, у якому система спочатку отримує релевантні зовнішні дані, а потім передає їх у контекст моделі. `GoogleSearch` демонструє пошукове доповнення, але в лабі немає векторного сховища або embeddings. |
| **MCP** | у цій лабі не використовується | Стандарт підключення зовнішніх інструментів і джерел даних до агента. Тут `GoogleSearch` підключено безпосередньо через ADK. |
